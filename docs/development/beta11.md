# β11の実装と検証

本ページはβ11の開発記録です。途中段階の件数・生成サイズは当時の測定値であり、最終状態の一覧ではありません。完成範囲と残る公開手順は[現在の作業計画](plan.md)を参照してください。

## 開始点と目的

β11は、[β10完成版](https://github.com/shogo314/rusk_b_10/commit/1f622e13c4afbfdac80e5afe8bad361cc1f0d400)を引き継ぎ、「ライブラリ拡充のための道具作り」を進めます。β10の[テストCI](https://github.com/shogo314/rusk_b_10/actions/runs/43277833759)と[文書CI・公開](https://github.com/shogo314/rusk_b_10/actions/runs/43277833846)は成功しています。実装範囲と検証結果は[β10の開発記録](beta10.md)に保存しています。

ライブラリ作者が、ユーザー定義型・共有・コピー・権限・コンパイル時の値を共通の規約で扱える基盤を整える方針です。個別のライブラリの追加範囲は、この基盤の仕様と併せて決めます。

## β11の実装範囲

| 分野 | 方向性 | 仕様として詰めること |
|---|---|---|
| 再帰型 | 木や永続データ構造などを型として記述する | struct・enumの直接・相互・ジェネリックな再帰、有限な値の構築、循環を切る操作、深い構造の解放・コピー |
| コピー | `__copy__`を共通の操作とし、標準ライブラリも利用する | 利用者向けの`copy`、コピー初期化・代入・配列・捕捉環境との接続、独自実装の契約 |
| 操作の自動生成 | struct・enumのコピー・等値比較・ハッシュを既定で生成し、手動定義を優先する | フィールドの要件、名前探索・衝突、必要時の診断 |
| キー | ユーザー定義型を辞書・集合へ接続する | `__hash__`と等値比較の規約、既存のキー操作との移行、格納後の変更と共有 |
| readonlyの表現 | 返却値・コンテナ要素の読み取り制限を表す | 型表記、外側と要素の権限、共有・コピー・変換・ジェネリック・externへの伝播 |
| コンパイル時の値引数 | 法や長さなどを型・具体化の指定に利用する | 構文、値の種類と同一性、推論、評価可能な操作、副作用・資源上限 |
| 空のstruct | タグや状態を持たない操作の型を記述する | 構築、型の同一性、コピー・代入・ハッシュ、externのABI |
| メタ情報 | 標準ライブラリから処理系の情報を取得し、生成C++にも由来を記録する | バージョンの識別、ソース情報の範囲、記録形式、再現性 |

以下の合意済み方針に従って、基盤を実装しました。値引数はInt・Boolのリテラルと値パラメータの受け渡しから始め、一般のコンパイル時関数評価は今回の初期実装に含めません。現在使える機能は[対応範囲](../reference/status.md)を参照してください。

## 実装と確認の順序

以下の分野ごとに実装・利用例・境界テストを接続します。循環共有と自動コピーは下記の方針に従います。

| 段階 | 内容 | 確認する利用例・境界 |
|---|---|---|
| 1 | 空のstructとコピー規約 | タグによるオーバーロード、手動・自動の`__copy__`、コピー初期化・代入・コンテナ・捕捉環境での一貫性 |
| 2 | 再帰型と寿命 | `Option`・`Vec`・enumを介する木、相互再帰、部分木の共有、深い構造の解放・コピー、循環を作る更新 |
| 3 | readonlyの型表現 | 返却した共有の変更禁止、外側だけ変更できるコンテナ、入れ子の権限、既存のmutableな別名との整合 |
| 4 | ハッシュ規約とユーザー定義キー | 独自struct・enumを使うDict/Set、等値比較とハッシュの一致、キーを変更する経路の遮断または分離 |
| 5 | コンパイル時の値引数 | 法の異なる型の区別、長さによる具体化、同じ値の具体化の共有、不正な値・評価失敗・資源上限の診断 |
| 6 | 全体の接続と検証 | ジェネリック・ローカル型・extern・整形・検索・API文書、通常版・最適化なし・リーク検査・公開問題 |

キーは格納・取得時にコピーする方式を維持し、ユーザー定義型へ対応します。readonlyな共有としてキーを公開するAPIは今回追加しません。コンパイル時の値引数は、再帰型の実装前提ではなく独立した設計項目です。

## 合意済みの方針：循環共有とコピー

以下をβ11の方針として採用し、再帰型と循環を切る操作を実装しました。

- 再帰型と実オブジェクトの循環共有を認めます。循環を切る責任は利用者が持ち、β11の前提としてGCや循環回収器は導入しません。
- 所有は参照カウントを基本とします。内部の循環は外側の変数を手放すだけでは解消されず、切り忘れた循環はリークします。
- 循環へアクセスできるうちに、通常のRusk操作で辺を切れるようにします。フィールドの共有先の結び直し、コンテナのclear・要素削除などを使い、コピーを必要とせず参照を手放せることを確認します。
- 参照を切っても、ほかの共有元があるオブジェクトは生存します。外側の名前を手放したことを理由に、生存中のオブジェクトのフィールドを処理系が勝手に消すことはしません。
- 自動生成する`__copy__`はフィールドごとの再帰コピーとし、各フィールドの`__copy__`を呼びます。Vecも要素ごとにコピーします。処理系はコピー先の対応表を暗黙に用意せず、複数の格納先が同じ値を共有していても、その共有関係を再現しません。
- 循環する値のコピーや、共有関係を保つコピーが必要な場合は利用者が`__copy__`を定義します。自動コピーには循環する値のコピーを完了させる保証を設けません。β11では循環検出を追加しません。深い非循環構造でも、無制限な深さのコピー・解放を保証しません。

## 合意済みの方針：手動定義と自動生成

以下を採用して実装しました。自動生成の対象はstruct・enumとします。再帰型そのものはstruct・enum、相互再帰、Vec・Optionを介する再帰を対象にします。

| 操作 | 手動定義がない場合 | 手動定義がある場合 |
|---|---|---|
| `__copy__` | 各フィールドの`__copy__`で新しいstruct、または同じvariantのenumを構築 | 手動定義を使う。等値比較・ハッシュの有無とは独立 |
| 等値比較`__eq__` | 宣言順に各フィールドの等値比較を行い、不一致で短絡 | 手動定義を使う。構造的なハッシュは自動生成しない |
| `__hash__` | 等値比較も自動生成する型では、各フィールドのハッシュを合成 | 手動定義を使い、等しい値は同じハッシュを持つことを利用者が保証 |

手動定義の有無は型の定義スコープで判定し、手動定義がなければ同じスコープに生成します。呼び出し位置によって生成の有無を変えません。enumのコピーは現在のvariantのpayloadをコピーし、等値比較はvariantとpayloadを比較し、ハッシュにもvariantを含めます。

独自の等値比較を定義した型をハッシュ可能な型として使う場合は、`__hash__`も手動定義します。ハッシュを使わない型にまで定義を要求せず、必要な操作が使えない場合は利用箇所で診断する方針です。フィールド型に必要な操作がない自動生成についても、利用時の要件として扱います。

循環する値の等値比較は利用者が実装します。自動生成は訪問済みの対応表や循環検出を暗黙に導入せず、循環する値に対する停止性を保証しません。循環する値をキーに使う場合は、等値比較と整合するハッシュも手動で用意します。循環のない再帰的な値は、必要なフィールドの操作があれば自動実装を使えます。

手動の`__copy__`は、子を共有したり入力そのものを返したりできます。通常の関数として返却する共有先と効果を解析し、名前だけで新規確保・独立性・readonlyの解除を仮定しません。利用者externにも既存の信頼契約の規則を適用します。

`copy(a)`と`let b = a`は`__copy__`へ統一します。既存の値への`b = a`は、外側の同一性を保つ`__assign__`が担当し、その内部で必要な`__copy__`を使います。配列の各要素や捕捉環境の各フィールドも同じコピー規約へ接続します。

### この方針に対する完成条件

- 自己循環・相互循環を構築し、通常のRusk操作で切った後、外側の共有も手放すと回収されることをリーク検査で確認します。
- 複数箇所から共有される値は、一つの辺を切っても残る共有経路から利用でき、二重解放・解放後のアクセスを起こさないことを確認します。
- 自動コピーで元の内部共有を再現しないことを、structとVecの両方で確認します。
- 手動の`__copy__`で独自のコピー方針を実装できることと、標準ライブラリからもその操作を利用することを確認します。
- 手動の等値比較がないstructは構造的な等値比較・ハッシュを使い、独自の等値比較があるstructでは手動のハッシュを使うことを確認します。必要な操作がない場合は利用箇所で診断します。
- 循環する値の等値比較を手動定義し、停止して期待する結果を返すことを確認します。ハッシュキーにする例では、等値比較とハッシュの整合も確認します。
- 共有を返す手動コピーを、独立した更新可能な値と誤認しないことと、代入が外側の同一性を保つことを確認します。

## β11で追加するメタ情報

標準ライブラリからバージョンなどのメタ情報を取得する手段と、生成C++に元のRuskコード・コンパイラに関する情報を記録する手段を用意します。ライブラリ拡充の道具と併せてβ11の対象に含めます。元のRuskコード全文を生成C++へ含めることは採用済みです。現在のAPI名と記録形式は[CLIと生成C++](../getting-started/cli.md)を参照してください。

### 標準ライブラリからの取得

- `compiler_version()`・`compiler_revision()`・`compiler_modified()`・`compiler_source_url()`で、生成に使ったRuskコンパイラの版・Gitリビジョン・変更の有無・公開元を取得します。β11のパッケージバージョンは`0.1.0-beta.11`とし、正式版`0.1.0`と区別します。
- 実行時に別のインストール済みコンパイラを探さず、その実行ファイルを生成した処理系の情報を返します。
- CLIの`rusk --version`、内部エラー報告、標準ライブラリ、生成C++で識別情報の取得元を共通化します。Git情報がない配布ソースからのビルドでも動作できる形にします。

### 生成C++への記録

- コンパイラの版・リビジョン、生成に影響するオプション、元のRuskソースを識別する情報を記録します。従来の固定ヘッダー`Generated by Rusk beta`を置き換え、由来を具体的に追える形にしました。
- 元のRuskコード全文を、生成C++内で人が読める形で記録します。本文をファイル名やハッシュだけで代替しません。入口のソース、利用者のinclude先、読み込んだ標準ライブラリのRusk全文を元の改行とともに記録します。
- コンパイラ・標準ライブラリの公開元URLと、生成に使った版・リビジョンを記録する方針です。独自ライブラリ・変更済み標準ライブラリ・externのC++資源についても、実際に使った内容と出典を対応させる方法を詰めます。
- 元コードを読めるコメントとして掲載できる形式を設計し、コメント終端・行末のバックスラッシュ・改行などがあっても生成C++を壊さず、元の本文を確認・復元できるようにします。現在は行ごとのコメントと、元の改行を含む本文を復元できるJSONコメントを併記します。
- 現在時刻や作業ディレクトリなど、生成のたびに変わる情報は追加しません。ソースの表示名は読込時の名前を保持します。

### 完成条件

- 実行したRuskプログラムから、生成に使った処理系を識別でき、CLIと生成C++の記録が一致します。
- 取得できないリビジョンを偽の値で埋めず、Gitのない配布ソースからもビルドできます。
- 同じ処理系・入力・オプションでは、メタ情報の追加によって時刻などに依存する差分を作りません。
- 複数のソースと特殊な文字を含むソースについて、情報の対応と生成C++のコンパイルを検証します。

### β期間と正式版0.1.0の扱い

β期間は本番のコンテストへ導入せず、不完全な対応でも段階的に実装・検証します。以下を正式版Rusk 0.1.0の公開前に確認する条件とし、β11の完成にすべてを要求するものとは分けます。β開始時のCargoの`version = "0.1.0"`は正式版の完成を表すものではなかったため、現在は`0.1.0-beta.11`へ変更しています。

- 元のRuskコード全文、include先、標準ライブラリ、extern資源について、提出物から内容・版・出典を確認できる範囲と方法を完成させます。
- 公開元URL・リビジョンが実際に使ったコードと対応し、未公開のローカル変更を公開版と同じものとして表示しないようにします。
- 出典・ライセンス表記を保持し、生成物へどの情報を載せるかを文書と検証に反映します。
- 提出サイズやC++のコンパイルへの影響を調べ、正式版公開時点のAtCoder規約と提出条件を改めて確認します。

examplesのライブラリを標準へ移す前の同日のローカル測定では、`wt "Hello";`の生成C++は約437 KB（十進表記）で、入口と標準ライブラリ計41ソースの本文を記録しました。本文を読みやすいコメントと復元用JSONで併記する方式にはサイズの負担があり、正式版では提出条件と併せて確認します。

2026年11月13日に確認した[AtCoder生成AI対策ルール（20261014版）](https://info.atcoder.jp/entry/llm-rules-ja)では、開催中のABC・ARC・AGCで、開始前にAIを使って作成したコードをコピーして使う場合、事前のWeb公開と参照URLの添付が条件です。全文掲載だけでこの条件を満たすとは扱わず、出典URLも設計対象に含めます。同規約にはバイナリ埋め込み前の元コードをコメントまたは事前公開URLで確認できるようにする規定もありますが、その規定を通常のRuskからC++への変換にそのまま適用するとは断定しません。

この項目は再帰型・readonly・値引数に依存せず、独立して実装できます。実装順序では早い段階に置けます。

## 実装上の境界と継続する確認

- 型の定義スコープでのジェネリックやローカル型の具体化と自動生成の優先規則、必要な操作がない場合の診断を引き続き検証します。
- ハッシュはフィールドを順に合成し、辞書・集合では既存の乱数化を維持します。キーのハッシュ・等値比較中に同じコンテナの探索・変更・走査へ再入した場合、内部の位置を無効化する前に実行時エラーにします。項目数の参照と別のコンテナへの操作は認めます。等値比較以外の比較操作は自動生成の対象に含めません。
- 深い非循環構造のコピー・解放は再帰処理を基本とし、任意の深さで安全に完了する保証は追加しません。循環共有の許可だけで、これらの操作の停止性やスタック使用量を保証することにはしません。
- readonlyは`readonly T`の型表記、要素と外側の区別、不変な型引数として実装しました。値引数は`N: Int`・`B: Bool`と宣言し、リテラルと値パラメータの受け渡しを対象に実装しました。

## 進め方

1. 代表的なライブラリと利用例を挙げ、必要な道具と期待する共有・コピー・失敗の規則を整理します。
2. 採用範囲、互換性、依存関係、実装順序、完成条件を確定します。
3. 仕様・実装・フォーマッタ・検索とAPI文書・現行リファレンスをそろえ、通常版と最適化なしで検証します。寿命と循環に関する変更は、リーク検査を含むサニタイザーでも確認します。

β11の実装と必要な全体検証を完了しました。空のstruct、再帰型、`__copy__`への統一、struct・enumの等値比較・ハッシュと独自キー、メタ情報APIと元のRusk全文コメントを実装しました。Int・Boolの値引数はリテラルと値パラメータの受け渡しに対応し、readonlyは返却・要素・フィールド・payload・捕捉・extern・不変な型引数へ接続しています。部分的なreadonlyを含む値の格納先の型と再帰コピーの効果を解析し、未知・変更・共有を返す手動操作を安全と仮定しないことも検証しました。ほかの候補は[将来の方針](../future.md)、設計上の論点は[未決定事項](https://github.com/shogo314/rusk_b_11/blob/main/design/review.md)を参照してください。

## examplesの実装の標準化

データ構造5実装と、剰余累乗・素数判定・Z-algorithm・LCS・グリッドBFSを標準へ移しました。[shogo-library](https://github.com/shogo314/shogo-library)を参考に、`data_structures/`・`math/`・`string/`・`dp/`・`graph/`へ分割しています。現行の標準ライブラリと同様にpreludeから自動読み込みし、解答例は入出力と利用処理を残しました。新しいデータ構造の追加やモノイド抽象への作り直しは今回の移動には含めていません。

`Fenwick`は`FenwickTree`へ改名し、操作名も`apply`・`prefix_prod`・`prod`へ統一しました。元のコピー・共有・半開区間の意味を維持し、旧example内のライブラリファイルへのincludeとベンチマーク・検証コードも更新しています。利用方法は[データ構造](../library/data-structures.md)と[アルゴリズム](../library/algorithms.md)を参照してください。
